# AI 请求可见性设计记录

## 目标

管理员需要在控制台看到所有已经进入 Niffler 的 AI 调用请求。只要请求打到 AI 公共入口，并且网关产生了响应，即使没有进入上游调度，也要能在“使用记录”里查到。

## 非目标

- 不记录后台管理接口、登录注册接口、静态资源和普通前端页面请求。
- 不把平台拦截记录计入扣费、套餐消耗或上游成本。
- 不新建独立的“进站日志”页面，避免管理员查问题时需要在两个页面之间跳转。

## 行为变化

以前只有进入 AI 执行或结算链路的请求会生成使用记录。入口阶段直接返回的错误，例如无效 API Key、余额不足、模型不允许、请求格式错误、用户限流等，只能在网关访问日志中看到。平台自己处理的 AI 请求，例如本地 `count_tokens`，也不会进入使用记录。

调整后，AI 公共入口的入口阶段失败也会写入 `usage`，包括认证拒绝、限流、请求体解析失败、上下文解析失败和没有可用执行路径：

- `status = failed`
- `billing_status = void`
- `provider_name = Niffler 平台`
- token 和金额为 0
- `request_metadata.source = platform_rejection`
- `request_metadata.platform_reason` 保存具体原因
- `execution_path` 保存网关返回路径

平台自己处理且没有上游成本的 AI 请求也会写入 `usage`：

- 2xx 响应写 `status = completed`
- `billing_status = void`
- `provider_name = Niffler 平台`
- token 和金额为 0
- `request_metadata.source = platform_handled`
- `request_metadata.platform_reason` 保存平台处理原因

因此这些请求会出现在现有“使用记录”列表和详情里，但不会触发钱包扣费。

## 页面位置

放在现有“使用记录”页面，不单独开新页面。

原因：

- 管理员排查请求时，核心问题是“这个请求最终发生了什么”，不应该先判断它属于使用记录还是入口日志。
- 同一页面能统一按用户、Key、模型、状态和时间检索。
- 平台拦截记录天然是失败请求，和上游失败、调度失败放在同一张表更容易对比。

## 影响范围

- 后端网关：在 AI 公共入口的早期拒绝分支写入失败使用记录。
- 使用记录列表：复用现有接口和页面，不新增数据库表。
- 计费：平台拒绝和平台本地处理记录使用 `billing_status = void`，不进入结算。
- 性能：只写 AI 入口失败，不记录管理后台和静态资源，避免扩大写入量。

## 验证方式

- 覆盖无效 API Key、模型不允许、余额不足、请求格式错误、入口限流、上下文解析失败和平台本地处理这类早期返回。
- 确认记录出现在使用记录查询结果中。
- 确认记录状态为失败，计费状态为 void，金额为 0。
- 确认已经进入调度链路的失败仍沿用原有执行失败记录。
