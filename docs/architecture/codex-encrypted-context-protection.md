# Codex 加密上下文保护

## 依据

OpenAI 官方文档说明，`reasoning.encrypted_content` 是加密后的推理内容；在 stateless 模式或零数据保留场景下，调用方需要保留这些 reasoning items，并在后续请求中原样带回。官方文档没有说明这类内容必须绑定同一个 API Key、同一个 OAuth 账号或同一个上游账号。

Niffler 不能解密 `encrypted_content`，也不能判断它能否被另一个上游账号继续使用。因此，“稳定路由到同一个上游账号”不是官方协议硬性要求，而是 Niffler 在多上游账号池场景下的安全策略。

## 目标

带 Codex 加密上下文的请求应尽量稳定路由到同一个上游账号，避免同一段上下文被多个账号反复尝试后增加失败和账号风险。

外部旧会话首次进入 Niffler 时，网关不能预先知道原本使用的是哪个上游账号；这种请求允许尝试接入一次，只有成功后才建立后续固定关系。

## 非目标

- 不尝试破解、解析或改写 Codex 的 `encrypted_content`。
- 不把 `encrypted_content` 自身当成稳定会话编号。
- 不新增会绕开既有调度记忆的临时会话维度。
- 不改变普通 OpenAI Responses 请求的调度逻辑。

## 行为变化

- Codex 请求如果包含 `encrypted_content`，优先使用明确会话标识固定账号。
- 明确会话标识包括 `x-aether-session-id`、`session_id`、`conversation_id`、`prompt_cache_key` 或已有通用会话字段。
- 如果没有明确会话标识，网关不再直接返回 400，而是继续使用“用户 Key + API 格式 + 模型”的既有调度记忆。
- 这样可以复用同一个用户 Key 前面请求已经固定过的上游账号，不会因为新造内部会话键而丢失既有记忆。
- 如果没有明确会话标识且命中 Codex 加密上下文接入场景，调度阶段不会因为第一次选中某个账号就提前写入固定关系。
- 这类请求只有在上游请求成功后，才会写入“用户 Key + API 格式 + 模型”对应的固定账号。
- 如果上游错误明确包含 `encrypted_content`，网关直接把这次失败返回给用户，不再继续换其它账号尝试。
- 对用户的实际影响是：外部旧会话如果无法接入，应新开会话；Niffler 内部成功建立过的后续会话会继续固定到同一个上游账号。

## 影响范围

- 只影响 Codex 客户端发出的 OpenAI Responses 请求。
- 不影响普通无加密上下文的请求。
- 不影响 Claude Code、OpenCode、Gemini CLI 的既有会话识别。

## 验证方式

- 单元测试覆盖 Codex 加密上下文无会话标识时允许继续，并保持无显式会话状态。
- 单元测试覆盖带 `x-aether-session-id` 时允许继续。
- 单元测试覆盖无显式会话的加密上下文请求不会在候选物化阶段提前写入固定账号。
- 单元测试覆盖上游返回加密上下文无效时，同步和流式路径都停止继续换账号。
- 单元测试覆盖非 Codex 请求不受影响。
