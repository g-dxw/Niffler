# Provider 账号用量与结算统计一致性

日期：2026-08-01

## 目标

- `usage`、`usage_settlement_snapshots`、套餐额度流水和钱包流水继续作为计费事实来源。
- Provider 账号累计费用和 Codex 窗口费用只统计已经完成结算的请求。
- 请求从 `pending` 变为 `settled` 时，结算事实、请求级统计贡献和统计增量在同一事务提交。
- 重复消息、重复结算和进程重试不能重复增加请求数、Token 或费用。
- Provider 累计统计和窗口统计可以从结算事实重建，错误的已有零记录也必须能够被识别和修复。

## 非目标

- 不改变套餐额度计算、钱包扣款顺序、销售价或上游基础成本计算。
- 不重新执行历史请求结算，不补扣或退款。
- 不改变 Codex 上游返回的额度百分比；本地窗口统计只表示 Niffler 已确认的结算用量。
- 不在本次改动中合并运行状态统计和结算统计。

## 已确认的问题

终态 usage 记录先写入数据库，结算随后执行。终态记录写入时
`billing_status` 仍为 `pending`，因此 Provider 账号请求数和 Token 已生成统计增量，
费用及窗口增量为零。结算事务只更新结算快照和 usage 的计费状态，没有再次计算
Provider 账号贡献，最终形成“请求数和 Token 有值、费用及窗口为零”的永久错误。

窗口自动重建原先只检查窗口记录是否缺失或 `rebuilt_at` 是否为空。错误零记录已经存在
且曾经重建时，这个检查不会再次比较结算事实，因此无法自行恢复。

## 设计

### 1. 请求级统计贡献

新增 `provider_api_key_usage_contributions`。每个 `request_id` 只保存一份当前已确认贡献：

- Provider 账号编号
- 请求数、成功数、失败数、Token、基础成本和响应时间
- 窗口请求数、窗口 Token、窗口基础成本
- 用量发生时间
- 单调递增的 `revision`

没有终态贡献时保留零值和非活动状态，不删除记录。这样请求失败恢复、账号变化或统计移除
后再次写入时，修订号仍然单调递增。

### 2. 统一事务内更新

usage 写入和结算完成后都调用同一个贡献同步函数：

1. 从当前 usage 与结算快照计算应有贡献。
2. 锁定请求级贡献记录。
3. 比较旧贡献和新贡献。
4. 更新贡献记录并增加修订号。
5. 按差额写入 Provider 累计统计和窗口统计事件。

结算事务必须先写入最终计费状态，再同步贡献，然后提交。任一步失败时，扣费、结算状态、
贡献记录和统计事件全部回滚，不能出现部分成功。

### 3. 幂等统计事件

请求级统计事件使用以下业务内容生成稳定 UUID：

```text
request_id + provider_api_key_id + contribution revision + projection kind
```

`usage_counter_deltas.id` 的主键负责拒绝同一事件重复写入。随机 UUID 仍用于与请求级贡献
无关的普通计数事件。插入统计增量统一使用 `ON CONFLICT (id) DO NOTHING`。

### 4. 统计口径

- Provider 账号请求数、成功数、失败数、Token 和响应时间统计终态请求。
- Provider 账号费用只统计 `billing_status = settled` 的上游基础成本。
- Provider 窗口请求数、Token 和费用只统计 `billing_status = settled`。
- 用户销售价、套餐扣费和钱包扣费不进入 Provider 上游成本统计。

### 5. 重建与历史修复

- Provider 累计统计和窗口统计都从请求级贡献表重建，不再从每次读取路径扫描完整
  `usage` 历史。
- 窗口检查同时比较当前投影与贡献表的请求数、Token 和费用；记录存在但数值错误时也会
  进入后台修复队列。
- 单个账号修复失败时保留队列记录，写入失败次数和错误原因，并延迟到下一次重试时间。
  该账号的错误不能阻止其他账号继续修复，也不能在每轮后台任务中立即重复执行。
- 数据库迁移只创建贡献表、迁移状态表、修复队列表和必要的小表索引。迁移会记录一个
  历史截止时间，但不会锁住 `usage`，也不会在启动事务中一次性回填。
- 新版本先对新请求持续写入贡献表。后台随后按账号领取任务，按
  `(created_at, request_id)` 小批量回填截止时间以前的历史请求。每个账号回填完成后，在
  统一的统计锁下重建累计统计和当前窗口，并吸收该账号尚未处理的旧统计队列。
- 统计写入、队列处理、账号重建使用同一套锁顺序：先统计总锁，再账号锁；请求贡献同步只
  获取账号锁。这样重建不会和增量处理交叉覆盖，也不会把同一请求重复加到账上。
- 历史修复只更新请求级贡献和统计投影，不调用结算入口，不改变套餐额度、钱包余额或流水。
- 贡献表保留到对应 `usage` 审计记录删除之后再清理；统计队列保留至少 7 天。迁移状态和
  修复队列保留，便于查看是否仍有账号未完成整理。

## 影响范围

- PostgreSQL usage 写入、结算事务、超时恢复和 Provider 统计增量。
- Provider 账号累计请求数、Token、费用和 Codex 窗口用量展示。
- 不影响用户实际扣费金额；修复后变化的是错误的 Provider 统计展示。

## 验证方式

- `completed + pending` 写入后统计请求数和 Token，费用与窗口为零。
- 同一请求结算为 `settled` 后只增加一次基础成本和窗口用量。
- 重复结算、重复终态消息和事务重试不重复统计。
- 结算失败时扣费和统计事件同时回滚。
- 已存在的错误零窗口能被检测并按结算事实重建。
- 超时恢复为 `settled` 时也产生最终 Provider 统计贡献。
- 迁移只建立状态，不会长时间阻塞业务写入。
- 后台分批回填会修复已有错误累计值，并且不会重复应用迁移前尚未处理的 Provider 增量。
- 重建与队列处理并发运行时，最终统计与贡献表一致。
- 单账号修复失败后会增加失败次数、保存错误原因并延迟重试，其他账号仍可正常处理。
- 两笔低于 8 位小数的费用分别按 8 位小数确认后，实时统计和重建结果一致。
- 运行 PostgreSQL 迁移测试、usage 仓储测试、结算测试和格式检查。
