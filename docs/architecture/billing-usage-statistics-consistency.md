# 计费和统计一致性口径

## 目标

统一请求计费、使用记录、Dashboard 和统计聚合的金额口径，确保用户侧看到的用量、价格、倍率和实际扣费可以互相验算，管理员侧可以对收入、上游成本和毛利做一致统计。

## 非目标

- 不合并全局模型价格和 Provider 模型价格。
- 不把 Provider、上游服务或上游账号暴露给普通用户。
- 不让 Dashboard、Usage 列表或统计接口重新计算历史请求费用。
- 不为当前没有接入的图片、视频、语音、文件处理等能力新增实际计费逻辑。

## 核心规则

每次请求只生成一张结算账单，所有页面和统计只读取这张账单或它的聚合结果。

用户消费公式固定为：

```text
用户消费 = 标准模型基础费用 * 用户倍率 + 独立计费项 + 内容审查费用
```

标准模型基础费用只包含：

- 输入 token 费用
- 输出 token 费用
- 缓存写入 token 费用
- 缓存读取 token 费用
- 按请求固定价

用户倍率只作用于标准模型基础费用，不作用于独立计费项和内容审查费用。

独立计费项用于表达不按模型 token 倍率计算的费用，例如图片、视频、语音、文件处理和特殊接口。当前没有实际接入的项目不主动扩展实现。

## 价格层级

全局模型价格是默认价，Provider 模型价格是覆盖价。

同一次请求的实际计费价格由调度结果决定：

1. 如果本次调度到的 Provider 模型设置了覆盖价，使用 Provider 模型覆盖价。
2. 如果没有覆盖价，使用全局模型默认价。
3. 结算完成后，历史请求只认结算快照里的最终生效价，不再查询当前模型价格重算。

用户侧可以看到“本次请求生效价”，不能看到 Provider 名称、Provider ID、上游服务、上游账号或“来自某 Provider 覆盖价”之类可以反推出上游的信息。

管理员侧可以看到全局默认价、Provider 覆盖价、最终生效价、价格来源、用户消费、上游成本和毛利。

## 统计口径

用户消费只统计已经结算的用户消费金额，判断条件是 `billing_status = 'settled'`。

平台成本只统计上游实际成本，读取结算事实里的 `actual_total_cost_usd`，不因为用户消费未结算而清零。

请求成功率、错误率、响应时间只属于技术统计，不能决定费用是否计入用户消费或平台成本。

Dashboard、Usage 表、每日统计、模型拆分和 Provider 拆分都不能重新套价格或按成功失败重算费用。

## 性能要求

结算时写清账单结构，统计时只做简单汇总。

列表页和 Dashboard 不应现场解析复杂 JSON 或按当前价格重算历史请求。单条请求详情可以按需展示完整可验算账单。

预聚合表可以继续保留，但只能缓存统一口径的结果，不能改变金额含义。

## 历史数据

新请求必须具备完整结算快照。旧请求如果缺少完整价格快照，只能尽量补齐；补不齐时展示为历史数据，不能假装完全可验算。

## 验证方式

- 同一时间范围内，Dashboard 总消费、每日消费、Usage 拆分消费必须一致。
- Provider 覆盖价和全局默认价分别命中时，请求详情能用结算用量、生效价和倍率验算用户消费。
- 用户侧接口和页面不返回或展示 Provider、上游服务、上游账号。
- 管理端能区分默认价、覆盖价、最终生效价、上游成本和毛利。
