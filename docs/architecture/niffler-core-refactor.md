# Niffler 核心模型重构设计记录

## 目标

本次重构把旧的 Provider、Endpoint、Key、User Group、价格和错误处理逻辑拆成更清楚的业务边界，后续统一按 Niffler 领域模型维护。

第 1 批只落地安全基础设施：设计文档、共享契约、影子表迁移和只读校验脚本。不接入现有生产请求链路，不改变线上调度、计费、分组、页面或接口行为。

长期目标如下：

- 上游服务只描述供给方，例如 Codex、Claude、OpenAI、Gemini、自定义 OpenAI 兼容接口。
- 上游账号只描述真实可调度凭证，例如 OAuth 账号、API Key、Service Account 或自定义 Header 凭证。
- 产品策略替代旧用户分组，决定用户能用哪些模型、按什么价格销售、是否公开可绑定。
- 用户 Key 只绑定一个产品策略，不再在 Key 自身重复维护可用 Provider、模型和格式规则。
- 价格、计费、调度状态和错误返回规则都有明确字段语义，不再依赖分散的兼容判断。

## 非目标

第 1 批不做以下事情：

- 不迁移旧数据。
- 不删除旧字段或旧接口。
- 不修改生产请求链路。
- 不修改管理后台页面。
- 不改变用户实际可用模型、扣费、请求错误内容或账号调度结果。

## 长期工程原则

- 需求字段和代码字段一一对应，避免一个字段同时表达多个业务含义。
- 新旧逻辑不长期双写；新页面切换稳定后，旧接口只读兼容 14 天，然后删除旧读写路径。
- 旧字段可比旧接口多保留一个数据库版本，只读归档；删除前必须有数据校验、回滚说明和线上观测结果。
- 大型重构分批上线，每批都能单独验证、单独回滚，不允许一次切换影响生产运营。
- 数据迁移必须分批、可暂停、可恢复、可重复校验，避免长事务和全表重写。

## 核心模型

### 上游服务

上游服务表示一类供给方，不直接代表某个账号。

典型字段：

- 服务名称：管理员可见名称。
- 服务类型：`codex`、`claude`、`openai`、`gemini`、`openai_compatible`、`anthropic_compatible`、`custom`。
- 默认 API 格式：用于生成默认端点和测试请求。
- 成本倍率：参与上游成本计算。
- 是否启用：停用后不能被产品策略选择，也不能参与调度。

### 上游账号

上游账号表示真实可调度凭证，属于一个上游服务。

账号状态统一为：

- 可用：允许参与调度。
- 停用：管理员手动关闭，不参与调度。
- 失效：认证失效或凭证不可用，不参与调度，需要修复凭证后恢复。
- 额度耗尽：官方额度或内部成本窗口耗尽，不参与调度，等额度恢复或管理员处理。
- 冷却中：短时间保护状态，冷却到期后可重新参与调度。

不再把“熔断探测”“测试失败”“配置不完整”作为长期账号状态。手动测试结果、配置检查结果、风险次数和调度保护状态应独立记录。

### 产品策略

产品策略替代旧用户分组，只回答三个问题：

- 用户能用哪些模型。
- 钱包按什么价格销售。
- 这个策略是否允许公开绑定到用户 Key。

产品策略不直接管理上游账号调度。供给侧配置在上游服务和上游账号里维护。

## 价格和计费

价格字段按以下语义统一：

- 模型基础价格：默认来自官方价格表，可定时同步；历史请求不重算。
- 第三方同步价：第三方接口返回的价格，只作为该上游的参考或可选成本基础。
- 上游成本价格：`基础价格 × 服务成本倍率 × 账号成本倍率`。
- 钱包销售价格：`基础价格 × 产品策略销售倍率`，允许模型级覆盖。
- 套餐消耗：按基础价格消耗，套餐倍率固定为 1。
- 结算快照：每次请求完成时保存当时使用的基础价、销售价、成本价和倍率，后续价格调整不影响历史记录。

## 调度和请求记录

长期请求链路应按以下顺序执行：

1. 校验用户 Key 状态和产品策略。
2. 校验模型是否在产品策略里可用。
3. 找到支持该模型且启用的上游服务。
4. 找到服务下状态为可用的上游账号。
5. 按账号调度策略选择实际账号。
6. 记录每一次尝试的服务、账号、状态、跳过原因、上游状态码和耗时。
7. 结算时写入价格快照和扣费快照。

请求记录里的供应商或账号不能再显示 `unknown`。没有实际请求到上游时，应显示平台拦截原因；已经请求到上游时，必须记录实际服务和账号。

## 错误返回设置

错误返回设置分为平台级和上游级。

平台级用于 Niffler 本地拦截错误，例如：

- 用户 Key 无效。
- 用户 Key 暂停。
- 余额不足。
- 套餐额度不足。
- 模型不在产品策略。
- 没有可用上游账号。
- 频率限制。
- 平台维护。

上游级用于已经请求到上游后的错误，例如：

- 上游返回风控关键词。
- 第三方上游在错误里加入客服信息或营销广告。
- 官方上游错误需要改成用户更容易理解的说明。
- 默认上游错误文案。

上游级处理顺序固定为：

1. 风控关键词。
2. 广告或客服内容替换。
3. 状态码文案。
4. 默认上游错误文案。

风控关键词命中后可以触发账号保护动作。动作只保留三种：只记录、暂停调度、停用账号。暂停时长只保留四种：10 分钟、1 小时、24 小时、手动恢复。

原始上游响应明文只保存给管理员审计和请求记录排查使用，普通用户和用户侧接口不能看到原始全文，除非规则选择追加说明。

## 性能和并发

- 调度读路径必须优先使用缓存和预计算状态，不能在每次请求里做多表重查询。
- 账号状态、额度窗口和风险统计需要可增量更新。
- 管理后台统计查询必须分页、限制时间范围并走索引。
- 迁移脚本不得做无条件全表更新；需要数据迁移时必须分批提交，并输出进度。
- 只读校验脚本默认不写数据库，线上执行时必须有超时和结果摘要。

## 分批上线计划

### 第 1 批：影子结构

新增设计文档、共享契约、影子表迁移和只读校验脚本。不接入运行时。

验收标准：

- 新契约类型能独立编译和测试。
- 迁移只新增影子表和索引，不修改旧表。
- 校验脚本只读，能输出旧数据迁移风险报告。

### 第 2 批：后台只读视图

新增 Niffler 模型只读 API 和管理后台只读页面，对照旧 Provider、Key、User Group、价格和请求记录，不允许写入。

本批只做“看清旧数据能否映射到新模型”，不做迁移和修复。后台负责统一聚合旧 Provider、Key、Routing Group、模型价格和最近请求记录，前端只展示聚合结果，不在浏览器里拼接旧表含义。

只读 API：

- `GET /api/admin/niffler-core/readiness?recent_days=7`
- `recent_days` 默认 7 天，允许 1 到 90 天。
- 返回影子结构状态、旧数据映射摘要、停用 Provider 引用、Key 自身残留限制、分组策略缺口、价格缺口、最近 `unknown/pending` 请求记录和路由跳过原因。
- 查询必须限制数量。最近请求记录默认只取 50 条问题样本，避免后台页面触发大范围扫描。
- API 只读取旧表和影子表元信息，不写 `niffler_*`，不修改旧 Provider、Key、分组、价格或请求记录。

管理后台新增独立页面“核心对账”。页面顶部必须明确标注“只读检查，不会修改数据”，并把风险按业务含义展示：

- 旧 Provider 能否映射为上游服务。
- 旧 Key 能否映射为上游账号。
- 用户分组能否映射为产品策略。
- 哪些停用 Provider 仍被分组引用。
- 哪些用户 Key 或 Provider Key 仍有自身限制。
- 哪些模型或 Provider 模型缺价格。
- 最近请求记录里哪些因为没有实际上游账号、结算未完成或旧兼容字段导致显示 `unknown/pending`。

验收标准：

- 新旧视图数量可对账。
- `unknown` 来源能在只读视图里定位。
- 不影响旧页面操作。

### 第 3 批：管理写入切换

新增上游服务、上游账号、产品策略、错误返回设置的写入入口。旧页面进入只读或迁移提示。

验收标准：

- 新页面能完成新增服务、账号、产品策略、价格和错误文案配置。
- 停用服务不能被产品策略选择。
- 用户 Key 只能绑定一个产品策略。

### 第 4 批：运行时灰度

按管理开关启用新调度和新结算快照，先灰度内部 Key，再扩大到指定产品策略。

验收标准：

- 新旧调度结果可对账。
- 钱包扣费、套餐消耗、上游成本和请求记录一致。
- 错误返回文案符合平台级和上游级规则。

### 第 5 批：旧逻辑下线

新链路稳定后，旧接口只读兼容 14 天。满足删除条件后移除旧写入逻辑、旧页面和旧字段读路径。

稳定标准：

- 连续 14 天无 P0/P1 计费或调度事故。
- 请求记录中实际请求到上游的记录不再出现 `unknown` 服务或账号。
- 用户 Key、产品策略、上游服务和上游账号的数据对账误差为 0。
- 管理员已不再使用旧 Provider/User Group 写入口。
- 回滚演练通过，且有最近一次数据备份。

## 需要持续验证的问题

- 旧 `api_keys.allowed_providers`、`allowed_models`、`allowed_api_formats` 是否还有真实业务依赖。
- 旧分组里允许的模型、允许的端点、允许的提供商和提供商模型价格之间是否存在冲突。
- 现有请求记录中 `unknown` 的具体来源。
- 停用 Provider 是否仍被旧分组配置引用。
- API Key 是否存在缺失分组、分组改名导致引用断裂、或产品策略缺失的问题。
