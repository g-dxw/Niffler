# 用量正文与图片大对象存储

## 目标

在开启完整请求记录时，不因为 PostgreSQL 磁盘压力或固定捕获上限而静默截断请求、响应和图片数据。数据库只保存用量审计所需的索引与元数据，完整正文和媒体内容保存到可扩展的大对象存储。

## 非目标

- 不改变 `basic` 记录级别的默认行为。未开启完整记录时，仍不保存完整请求和响应正文。
- 不把图片 Base64 继续复制到 PostgreSQL 的 JSON 或 `bytea` 字段。
- 不因审计存储失败阻断用户正常请求；存储失败必须记录为明确的 `unavailable` 状态，不能伪装成完整保存。
- 不在本次改动中迁移所有历史 `usage_body_blobs`。历史数据继续按原逻辑读取，后续单独执行迁移。

## 设计

### 存储分层

- PostgreSQL：保存 `request_id`、正文类型、对象键、内容类型、编码、字节数、SHA-256、创建时间和存储状态。
- S3 兼容对象存储：保存完整 HTTP 正文、SSE 流和图片二进制。生产环境使用 S3、Cloudflare R2 或 MinIO；本地单机使用可配置的文件对象存储。
- 管理接口读取正文时，后端从对象存储取回内容，不把永久公网 URL 暴露给用户。
- 流式上传使用不可变的随机对象键，不覆盖同一请求的旧版本；非流式 JSON 正文使用原文 SHA-256 作为内容寻址键，同一请求重复写入相同正文时复用已有对象。数据库提交失败时只清理本次上传且仍未被数据库引用的对象；提交成功后再清理已经被新版本替换的旧对象。

### 完整记录行为

- `basic`：不创建正文对象。
- `full`：不再使用 `256 KiB` 作为完整性上限。流式响应使用分片上传，内存只保留小块缓冲和用量解析所需的有限窗口。
- 对象上传成功后，审计记录状态为 `reference`，数据库保存对象引用。
- 对象上传失败后，审计记录状态为 `unavailable`，同时保存失败原因、请求 ID 和可用的大小/哈希信息；不得写入截断正文并标记为成功。

### 图片处理

- 第一阶段将包含 Base64 图片的完整请求/响应 JSON 或原始响应流整体保存到对象存储，PostgreSQL 不再保存 Base64 正文。
- 后续若需要图片独立预览，再从正文对象中提取图片二进制并保存独立对象；这不是保证正文完整性的前置条件。
- 管理接口读取正文时仍走统一的正文引用，不直接暴露永久公网地址。
- 清理时先删除对象，成功后再删除元数据和正文引用；对象删除失败时保留数据库引用并记录失败。
- 上传和数据库提交不是同一个分布式事务。正常错误路径会立即做引用检查和清理；进程在对象上传与数据库提交之间突然退出时，仍需要后续对象存储生命周期规则或孤儿对象扫描处理极少量残留对象。

## 影响范围

- 用量运行时：移除完整记录路径上的静默截断，增加流式对象上传和失败状态传递。
- PostgreSQL 用量仓储：增加大对象元数据表，保留旧 `usage_body_blobs` 作为历史兼容读取路径。
- 网关启动配置：增加对象存储地址和前缀配置，凭据使用对象存储客户端支持的环境变量。
- 管理端查看接口：继续返回统一的正文内容，不要求前端区分数据库正文和对象正文。

## 验证方式

- 完整记录模式下，超过 256 KiB 的文本、SSE 和 Base64 图片响应可完整恢复，内容哈希一致。
- 对象存储不可用时，审计状态为 `unavailable`，不会出现 `truncated` 假成功。
- `basic` 模式不产生对象上传。
- 清理和历史数据库正文读取不回归。
- 覆盖本地文件对象存储和 S3 兼容配置解析测试。
